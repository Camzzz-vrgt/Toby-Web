PROJECT STRUCTURE

- index.html and dltrn.html are the main launchers and should remain synchronized.
- tobywebsinglefile.html is the downloadable launcher that loads game assets from the Camzzz-vrgt/Toby-Web GitHub CDN.
- Game files belong under files/<short-lowercase-name>/.
- Games normally open inside the launcher using an existing loadRemotePage-style function.
- Cards in the Mods and Extras tabs use filter categories.
- Mobile controls use files/mobile-controls.js and are disabled by default.
- Update 1.2 work is tracked in TODO.md.

RULES

1. Work inside the existing Toby-Web repository. Do not create another repository.
2. Create a separate Git branch for your work.
3. Do not push directly to main.
4. Do not modify or delete unrelated ports.
5. Do not rewrite established launcher systems unless the port genuinely requires it.
6. Everything required by the port must be stored inside the repository.
7. Do not depend on GameBanana, GameJolt, itch.io, jsDelivr, raw GitHub, or another website for required runtime assets.
8. External links may remain only for credits and navigation.
9. Do not add advertisements, trackers, or unrelated scripts.
10. Keep every individual Git object below GitHub's 100 MB hard limit.
11. Split large game files when necessary and reconstruct them in the browser.
12. Never silently replace missing files with placeholders. Clearly report anything missing.
13. Use existing Toby Web patterns and runners whenever possible.
14. Do not add temporary archives, extracted installers, debugging screenshots, tools, or development junk to Git.

DEPLOYMENT RULES

- You only push your work to GitHub.
- Commit the finished port to your separate branch.
- Open a pull request into Camzzz-vrgt/Toby-Web.
- Do not merge the pull request yourself.
- Do not upload anything to Cloudflare R2.
- Do not use Wrangler.
- Do not modify Cloudflare Workers, DNS, domains, or buckets.
- Do not use or modify AWS.
- Camzzz handles reviewing, merging, and deploying the port.
- Your responsibility ends when the tested GitHub pull request is ready.

PORTING PROCESS

1. Identify the exact game/mod version and engine:
   - DELTARUNE data mod
   - UNDERTALE data mod
   - DELTAMOD package
   - GameMaker
   - Kristal/LÖVE
   - Unity
   - Create Your Frisk
   - Another engine

2. Inspect the complete package structure before editing.

3. Determine whether it contains:
   - A patch requiring a base game
   - A replacement data.win
   - A DELTAMOD package
   - A complete standalone game
   - External music or data files
   - Custom saves or configuration

4. Find the closest working Toby Web port using the same engine.

5. Reuse that port's established runner and folder layout where appropriate.

6. Do not use the YoYo runner for a DELTARUNE or UNDERTALE data mod merely because it uses GameMaker. Follow the existing compatible mod-runner architecture.

7. Do not invent a new runner until existing compatible runners have been ruled out.

8. Copy only files required at runtime into:
   files/<port-name>/

9. Create a responsive index.html for the port.

10. Include the shared mobile controls in every applicable runner page:

   <script src="../../mobile-controls.js"></script>

   Adjust the relative path for the port's folder depth.

11. Add a square, correctly cropped icon. Do not stretch, blur, or unnecessarily pixelate it.

12. Integrate the port into:
   - index.html
   - dltrn.html
   - tobywebsinglefile.html when technically compatible

13. Add:
   - The game/mod card
   - Correct Mods or Extras placement
   - Correct filter category
   - Loader function
   - Creator and source credits
   - Porting credit where appropriate
   - An Update 1.2 changelog entry
   - A completed checkbox in TODO.md only after testing succeeds

CREDITS

TESTING

Start an HTTP server from the repository root on port 2000.

Test through:
http://localhost:2000/dltrn.html

Never test through file://.

Required testing:
- Launch through the real Toby Web card
- Launch through the direct localhost URL
- Get past the title and loading screens
- Play representative gameplay
- Test keyboard controls
- Test music and sound effects
- Test transitions and battles
- Test save loading and writing
- Test refresh and relaunch behavior
- Enable optional mobile controls and test movement, confirm, and cancel
- Inspect the browser console
- Inspect network requests
- Check for crashes, 404s, MIME errors, remote dependencies, missing audio, incorrect game speed, and infinite loading screens
- Reproduce and fix known later-game errors where practical

A title screen appearing does not count as a completed port.
